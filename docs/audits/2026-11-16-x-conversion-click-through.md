# X conversion click-through and server-side delivery — November 16, 2026

Request: keep the existing KBH pricing, copy, and checkout flow while making the existing X Ads Pixel `rht3t` measurable from `/join` through Stripe-confirmed trial or paid membership. Do not spend on ads.

Before: the public build loaded the X base pixel and already had browser event IDs for checkout, trial, and purchase. X auto-creates Site Visit and Landing Page View from the base pixel, but Events Manager had not shown the lower-funnel events as Active. Checkout attribution did not retain `twclid` through Discord OAuth and Stripe, and the Stripe webhook did not send server-side X conversions.

After: consented `twclid` is validated and retained with the current browser attribution, sent with checkout preparation, persisted on the existing checkout association, and copied to both Stripe Checkout and subscription metadata. The direct legacy checkout path also accepts it only when the browser asserted tracking consent. The webhook attempts the existing trial (`tw-rht3t-rhuz5`) and purchase (`tw-rht3t-rhuz6`) events via X's documented Ads Conversion API using the same opaque `conversion_id` as the browser pixel. The CAPI `event_id` is the event suffix (`rhuz5`/`rhuz6`). A first positive post-trial invoice may create the first purchase event; ordinary renewals are not new purchases. Stripe billing and VIP work never wait on marketing delivery. The CAPI sender is inactive until all four X Ads OAuth secrets are configured; it sends only a consented `twclid`, event type, opaque conversion ID, time, and actual paid value/currency. No email, phone, Discord ID, or raw Stripe ID is sent to X. No secret is logged.

Affected files: `analytics.js`, `membership.js`, `index.html`, `join.html`, `membership.html`, `cloudflare/kobes-checkout-worker.js`, `scripts/prepare-public-site.mjs`, and focused tests.

Verification: 133 focused tests passed for click-ID persistence, no send without credentials or click ID, OAuth request shape, the pre-existing browser event IDs/deduplication, checkout-worker behavior, and public build whitelist. `npm run build:site` prepared 117 production entries; a Wrangler production-config dry run bundled the Worker. Record Worker/site deployment IDs, site/browser checks, and X Events Manager status after release. No synthetic trial or purchase should be sent merely to turn an event Active.

Remaining: X Ads API access and four Worker secrets (`X_ADS_CONSUMER_KEY`, `X_ADS_CONSUMER_SECRET`, `X_ADS_ACCESS_TOKEN`, `X_ADS_ACCESS_TOKEN_SECRET`) are not configured. X Events Manager Active requires an actual consented eligible event and a live Ads Manager check. The base pixel's Landing Page View is automatic for a real ad landing; there is no separate configured landing event ID to invent.
